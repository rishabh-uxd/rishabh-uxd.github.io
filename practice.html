Practice

Tools, agents, and documentation

The case studies are things I shipped to customers. These are things I built for the people I work with: a review tool, an accessibility standard, an agent, and the playbook the agent came out of. Each one exists because a team kept hitting the same wall.

01

Raising the accessibility bar

Servicing launched with 7 accessibility launch blockers. Finding them late meant an annotation, a fix, and a re-review for each one, and the same categories of defect kept arriving with the next set of mock ups. I wrote the accessibility documentation the design and product groups now work from, covering reading order, heading levels, roles, names, states, and what has to be annotated before a hand off. Every iteration launch since has gone out with zero blockers.

Getting a review done and approved was the other half of the problem, so I built Design Insight. I check a design against the documentation with it before a review starts, and it lists what is missing, so a reviewer opens a file that has already been corrected. An accessibility approval now takes about a week, down from three and a half.

02

Building with AI

A designer who wants to show a stakeholder a working screen has to either build it by hand or wait for an engineer. I built an agent that takes a plain English request and returns a runnable prototype on the real design system, which saves about two and a half hours every time someone would otherwise have assembled one. A terminal is the whole interface: a sentence in, a prototype out.

The agent came out of a playbook I wrote for building with AI, which is what the rest of the group works from now. It covers where an agent belongs in a design process and where it does not, how to write a brief an agent can act on, what has to be checked by a person before anything is shown, and how to keep generated work on the design system. It contains:

  • A brief format. What an agent needs to be told, in the order it needs telling.
  • A review gate. The checks a person runs before generated work leaves the room, accessibility first.
  • Design system rules. How to keep an agent inside the tokens and components instead of inventing new ones.
  • Worked examples. The prototyper agent, start to finish, including what it got wrong.

The playbook has no adoption figures yet, so this section makes no claim about its impact. The two figures above are the measured ones.
